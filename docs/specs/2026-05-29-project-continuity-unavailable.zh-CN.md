# Project Continuity 不可用决策

状态：已接受
日期：2026-05-29

English version: [2026-05-29-project-continuity-unavailable.md](2026-05-29-project-continuity-unavailable.md)

## 决定

`project-continuity` 标记为不可用，但不删除 skill 目录。仓库继续保留它的 `SKILL.md`、`references/`、`assets/` 和 `agents/` 文件，用作历史记录、复盘材料和未来迁移参考。它不再用于初始化、继续、修复或管理跨 session 的长期项目状态。

## 原因

实验证明，这种工作模式对状态的依赖过强。它要求 agent 在每个 session 中持续、严格、正确地维护 durable state、handoff、lease 边界和下一步命令。但真实交互中，用户的指令会不断插入、改变优先级、跳过原定流程，或者要求马上处理新的问题。这些正常的用户行为会干扰状态更新，使状态文件很容易和真实项目进展脱节。

一旦连续性中断，后果会被放大。新开的 session 会把旧状态当作可靠上下文，而这些状态可能已经不完整、过期、冲突，甚至描述了错误的项目局面。这样的状态不只是帮助变少，而是会主动误导后续 agent，让它基于错误前提继续规划或交付，整体项目情况会迅速变得灾难。

这个 skill 也高度依赖模型智力。它要求模型能稳定理解项目边界、识别用户插入指令是否改变 lease、修复状态冲突、判断哪些文件能改、哪些信息必须写入 handoff。如果模型推理能力下降，交付质量会明显恶化：计划边界会漂移，状态修复会变成猜测，handoff 会制造虚假确定性，长期项目管理反而更不可靠。

## 影响

- 不再推荐 `$project-continuity` 作为长期项目的入口。
- 不再把 `/goal $project-continuity` 作为下一次 session 命令。
- 不再从该 skill 复制 continuity templates 到目标项目。
- 已存在的历史文件保留，方便审计它为什么失败、哪些想法可复用、未来是否能拆成更安全的小工具。

## 后续方向

如果未来重新设计类似能力，应避免把项目正确性绑定到一个庞大的 durable state 系统上。更安全的方向是采用更小、更局部、更可验证的机制，例如单次任务 handoff、明确的人工确认点、只读项目摘要、或者由确定性脚本生成的状态快照。任何新方案都应该能在用户频繁改指令、模型能力波动、状态局部缺失时保持可恢复，而不是把错误状态传递给下一次 session。
